# Using GaPSE from Jupyter notebooks

GaPSE is currently **unregistered**, so notebooks should use a separate Julia environment and refer to GaPSE through its local path.

This directory already carries the right `Project.toml`, so **as a user you only need**

```julia
julia> using Pkg

julia> Pkg.activate(".")        # from inside this directory

julia> Pkg.instantiate()        # once for all, downloads and installs everything, GaPSE included
```

`Project.toml` is tracked by git, `Manifest.toml` is not: it is rebuilt by `instantiate` on each machine.

Below we explain how that `Project.toml` was made, in case you need to recreate it.
The same approach applies to the notebooks inside `../theory` or to any personal directory of yours.

> [!IMPORTANT]
> You don't have to run the following commands, because we provide already a correct `Project.toml` file.
> We just show how we did it, for your information.

<br>
<br>



## TL;DR


```bash
# 1. declare the directory as a workspace member of GaPSE, in the TOP-LEVEL Project.toml:
#
#      [workspace]
#      projects = ["test", "docs", "ipynbs", "theory"]
#
# 2. then, inside it, add what the notebooks need - GaPSE included:
mkdir -p ipynbs && cd ipynbs
rm -f Project.toml Manifest.toml
julia --project=. -e 'using Pkg; Pkg.add(["GaPSE", "Plots", "LaTeXStrings", "DelimitedFiles", "Printf", "Dierckx", "GridInterpolations"])'
julia --project=. -e 'using Pkg; Pkg.instantiate(); Pkg.precompile()'
```

`Pkg.add("GaPSE")` resolves to the *workspace root*, which is GaPSE itself, so it writes the entry
(with its UUID) into `[deps]` and nothing else is needed: no path, no `Pkg.develop`, no `[sources]`
table. There is one `Manifest.toml`, at the top level, shared by every member of the workspace.

<br>



## 1. Re-creating the `ipynbs` notebook environment

We will assume the following dir structure

```text
GaPSE/
├── Project.toml
├── src/
│   └── GaPSE.jl
└── ipynbs/
    └── ...
```

and we will re-create the `Project.toml` needed for this directory.


First, the directory has to be declared a **workspace member** of GaPSE. That is done once, in the
*top-level* `Project.toml`:

```toml
[workspace]
projects = ["test", "docs", "ipynbs", "theory"]
```

Then everything else is ordinary `Pkg` usage:

```bash
$ cd ~/my-path/GaPSE
$ mkdir -p ./ipynbs
$ cd ./ipynbs
$ rm -f Project.toml            # we recreate it from scratch
$ julia

julia>                          # enter Pkg mode by typing "]"  => prompt will change
(@v1.12) pkg> activate .        # activate the current dir project  => prompt will change again
(ipynbs) pkg> add GaPSE         # resolves to the workspace ROOT, i.e. the GaPSE of this repository
(ipynbs) pkg> add Plots, LaTeXStrings, DelimitedFiles, Printf
(ipynbs) pkg> add Dierckx, GridInterpolations
(ipynbs) pkg> instantiate       # resolve the dependency graph, write the shared Manifest.toml, download and install everything in it
(ipynbs) pkg> precompile        # compile the source code of these packages into efficient cached artifacts (.ji files)
```

This creates `ipynbs/Project.toml`, and writes into the **shared** `Manifest.toml` at the top level of
the repository - not into an `ipynbs/Manifest.toml`, which a workspace member does not have.

NOTE: `add` already resolves the dependency graph, writes the manifest and installs everything, so
`instantiate` right after it has actually nothing left to do; it is the command *another* user needs, who starts
from the `Project.toml` committed here.

The resulting `Project.toml` will have the essential structure:

```toml
[deps]
GaPSE = "d1bf0294-456c-4ffb-813c-36d532d2da2e"
Plots = "..."
LaTeXStrings = "..."
```

No path to GaPSE appears anywhere: the workspace membership is what carries that information, and it is
recorded in the top-level `Project.toml`, which git tracks.

NOTE: the exact UUIDs and additional entries should be generated by `Pkg`, rather than written manually.

## 2. Why at all we need to do that?

### 2.1 Julia Notebook Environment

> [!IMPORTANT]
> A Julia kernel (for a Jupyter Notebook) has by default as active environment the directory of the notebook itself!

This is not a coincidence: the default kernel that IJulia installs runs Julia with the
`--project=@.` flag, and `@.` means *the nearest `Project.toml` at or above the working
directory*. Since the kernel starts in the folder of the notebook, a `Project.toml` sitting
next to it becomes the active project, and no cell has to do anything about it.
See [IJulia, "Julia projects"](https://ijulia.org/stable/manual/usage/#Julia-projects).

Two consequences worth knowing:

- `@.` walks **up** the tree. If this directory had no `Project.toml`, the kernel would
  activate the one of the repository root, i.e. GaPSE's own package environment - which is
  the wrong one for a notebook, and is also why forgetting the `Project.toml` gives confusing
  errors rather than a clear one;
- if you install your own kernel *without* that flag (the IJulia docs explain how), the
  active project is the global `@v1.x` one instead, and `using GaPSE` will not find anything.
  In that case run `Pkg.activate(@__DIR__)` yourself in the first cell, or install the default
  kernel with `IJulia.installkernel("Julia", "--project=@.")`.

=> There are **two different Julia environments** that come into play:

```text
GaPSE/Project.toml   ->  dependencies of the GaPSE package  ->  TwoFAST, FFTW, HCubature, ...

ipynbs/Project.toml  ->  dependencies of the notebook       ->  GaPSE, Plots, LaTeXStrings, ...
```

=> The notebook does **not** need to list GaPSE's dependencies again!

For example, if the notebook contains a cell with:

```julia
using GaPSE
using Plots
using LaTeXStrings
```

then:

* `GaPSE`, `Plots`, and `LaTeXStrings` are direct dependencies of the **notebook environment**;
* `TwoFAST`, `FFTW`, `HCubature`, etc. remain dependencies of **GaPSE**.

Julia resolves the dependency graph recursively, so GaPSE can load its own dependencies from its own `Project.toml`.

**A package should be added to the environment that directly uses it.**

This also means that a package reached *through* GaPSE needs no entry here: `GaPSE.TwoFAST.xicalc(...)`
works with `using GaPSE` alone, and only a bare `xicalc(...)` would require `TwoFAST` in this
`Project.toml`.



### 2.2 Pay attention to how your kernel was built

`--project=@.` is not something Jupyter knows about: it lives in the **kernelspec**, the
JSON file that tells Jupyter how to start Julia
(`~/.local/share/jupyter/kernels/julia-1.x/kernel.json`, or `~/Library/Jupyter/...` on macOS):

```json
"argv": ["/path/to/julia", "-i", "--color=yes", "--project=@.",
         "-e", "import IJulia; IJulia.run_kernel()", "{connection_file}"]
```

That file is written by IJulia's **build step** (`deps/build.jl`, run by `Pkg.add("IJulia")`
or `Pkg.build("IJulia")`) with one line - `installkernel("Julia", "--project=@.")`. The flag
is there because the *default* kernel puts it there; a kernel you install yourself gets only
the options you pass.

The kernel can then load IJulia and GaPSE from two different environments because Julia does
not search only the active project: `LOAD_PATH` is `["@", "@v#.#", "@stdlib"]`, i.e. the
active project (`ipynbs/Project.toml`, where GaPSE is), *then* the global default environment
(`~/.julia/environments/v1.12`, where IJulia is), then the stdlib.

Two consequences:

- keep IJulia in the **global** environment (`(@v1.12) pkg> add IJulia`); if it only exists in
  a project environment the kernel cannot start, and Jupyter says `Connection failed`;
- if you build your own kernel, keep `--project=@.`, or the active project becomes the global
  one and `using GaPSE` finds nothing. To restore the default:
  `using IJulia; IJulia.installkernel("Julia", "--project=@.")`.

From inside a notebook, `Base.active_project()` and `Base.load_path()` show what you got.

<br>



### 2.3 Why `include` is not the right solution?

Do **not** use `include("../src/GaPSE.jl")` to use GaPSE as a package!

In Julia, `include` only evaluates the source file, i.e. it's like you are copy-pasting the whole code in that cell.
It does not make Julia treat GaPSE as a package dependency with its own dependency environment.

Concretely, the `using TwoFAST` inside the GaPSE sources is then resolved against the *notebook's*
environment, and the include dies with

```text
LoadError: ArgumentError: Package TwoFAST [0dd23c3e-f403-11e8-3e11-4dddf690af97] is required
but does not seem to be installed
```

Instead, use `using GaPSE` with GaPSE declared in the notebook environment:

```toml
[deps]
GaPSE = "d1bf0294-456c-4ffb-813c-36d532d2da2e"
```

and with this directory listed in the `[workspace]` table of the top-level `Project.toml`. The
workspace is what tells Pkg where that UUID lives: a member shares the manifest of the workspace root,
and the root here is GaPSE itself.

NOTE: an earlier version of this environment used a `[sources]` table instead,
`GaPSE = {path = ".."}`, which is the general mechanism for an unregistered dependency and still the
right one when the package is *not* the root of your workspace. It was dropped here because a
standalone environment carries a `Manifest.toml` of its own, which records GaPSE's dependency list as
it was when that manifest was last resolved: adding a dependency to GaPSE then broke `using GaPSE` in
the notebooks with

```text
ArgumentError: Package GaPSE does not have Dates in its dependencies
```

until a `Pkg.resolve()` was run in *this* directory - and running it in GaPSE's own environment, which
is the natural thing to try, does not help, because that is a different environment with a different
manifest. A workspace member has no manifest of its own, so it cannot drift.

## 3. Which backend

These notebooks select `gr()`, the default backend of `Plots`, and no Python backend is
declared any more. Under Julia 1.12 `pythonplot()` (PythonPlot.jl) prints, on the first
figure,

```text
WARNING: Detected access to binding `Plots._py_drawfig` in a world prior to its definition world.
  !!! This code will error in future versions of Julia.
```

because `Plots` `include`s `src/backends/pythonplot.jl` lazily, the first time the backend
is selected, so the bindings it defines come into existence in a *later world age* than the
code that calls them. The other matplotlib backend, `pyplot()` (PyPlot.jl), is already
implemented under `Plots/src/backends/deprecated/`. GR needs no Python at all - `GR_jll`
ships its own binary - and draws everything these notebooks use, `st = :surface` and
`heatmap` included. To get matplotlib back: add `PythonPlot` here and call `pythonplot()`;
the warning is noise, not a failure.
